01 / Du conseil à l’action

Qu’est-ce qu’un coding agent ?

Jusqu’ici, tu as demandé des textes et des images. Un coding agent, ou agent de programmation, peut aussi utiliser des outils pour lire un projet, modifier ses fichiers et exécuter des commandes, selon les accès qui lui sont accordés.

Il peut enchaîner plusieurs actions : lire le code, proposer une modification, l’écrire, essayer de compiler, puis corriger une erreur. Le résultat se retrouve dans les fichiers du projet.

  1. Tu donnes une intention.

    « Réaliser l’accueil à partir de cette maquette. »

  2. L’agent travaille avec les outils disponibles.

    Il repère l’écran existant et prépare les changements utiles.

  3. Tu observes le résultat.

    Tu relis les modifications et tu lances l’app pour vérifier le comportement.

L’agent peut mal comprendre une demande ou produire une erreur. Les notions du cours t’aident à expliquer ce que tu veux conserver et à comprendre ce qu’il a fait.

💡

Coding agent · agent de programmation

Un assistant qui peut agir sur le code avec des outils, en plus de répondre dans une conversation.

💡

Outil · tool

Un moyen d’agir : lire un fichier, le modifier ou exécuter une commande, par exemple.

💡

Desktop · application de bureau

Une application installée sur l’ordinateur. Ici, elle sert à travailler avec le projet local.

02 / Préparer le bon contexte

Ouvre ton clone Android dans l’application desktop.

Avec l’encadrant, prépare l’application d’agent et son accès au compte. Codex est l’exemple utilisé ici ; les noms et la place des commandes peuvent évoluer. L’objectif reste d’ouvrir le bon projet local et de comprendre où les changements seront faits.

  1. Dans Android Studio, retrouve le chemin du clone de ton quiz, celui qui contient app/, settings.gradle.kts et gradlew.
  2. Dans l’application desktop, ajoute ou sélectionne ce dossier comme projet local. Choisis le travail dans ce dossier sur cet ordinateur, avec l’encadrant.
  3. Vérifie que c’est bien ton clone Android, et non le dossier HTML du guide. L’agent et Android Studio doivent travailler sur le même dossier.
  4. Regarde l’état Git avant de commencer. S’il existe des modifications, identifie-les avec l’encadrant et conserve le travail utile avant cette nouvelle étape.
  5. Prépare une branche dédiée selon la convention de l’équipe, par exemple mp/design_quiz_home en remplaçant mp par tes initiales.

Le guide suppose que ton clone contient le quiz réalisé pendant les leçons précédentes : questions, presenter, réponses et score. S’il contient encore seulement l’exercice « Click me », reprends avec l’encadrant au bon point du parcours avant de demander un nouvel accueil.

Le choix local de Codex permet de travailler dans le dossier courant. Ses autres environnements sont présentés dans la documentation officielle ; ils ne sont pas nécessaires pour cet exercice.

💡

Projet local · local project

Le dossier de travail présent sur ton ordinateur. Le sélectionner donne un contexte de fichiers à la conversation.

💡

Branche · branch

Une ligne de travail Git pour regrouper tes modifications. Ici, elle permettra de revoir le travail sur l’accueil.

03 / Une première demande de lecture

Fais repérer le code avant de le modifier.

Commence par une demande courte qui ne change aucun fichier. Elle te permettra de comparer les explications de l’agent à ce que tu connais du projet.

Lis le projet Android ouvert sans modifier les fichiers.
C’est mon quiz Kotlin/Compose réalisé pendant un stage de troisième.

Repère le point d’entrée, l’écran qui affiche les questions,
le modèle Question et le rôle du presenter.
Explique simplement le trajet d’un clic sur une réponse.
Indique les fichiers que tu as réellement lus.
Si un élément manque, signale-le au lieu de l’inventer.

Ouvre un des fichiers cités dans Android Studio. Reconnais-tu la fonction ou la classe décrite ? Si la réponse ne correspond pas au projet, vérifie le dossier sélectionné et précise le contexte avant de poursuivre.

Le bon contexte vaut mieux qu’une supposition.

Le nom d’une fonction ou l’organisation d’un projet peut avoir changé. On demande à l’agent de lire ce qui existe réellement avant de lui expliquer quoi ajouter.

💡

Contexte · context

Les informations disponibles pour comprendre la demande : les fichiers accessibles, tes explications et les références fournies.

04 / Donner une tâche limitée

Demande de réaliser seulement l’accueil.

Prépare home-design.txt, ou le document équivalent que tu as conservé, et ta maquette d’accueil. Joins ou sélectionne les références avec les moyens de l’application. Demande à l’agent de confirmer ce qu’il a pu consulter ; un chemin écrit dans le message ne garantit pas que le fichier est accessible.

Adapte le prompt à tes textes et à tes fichiers. Si tu as une illustration séparée, indique laquelle utiliser. Sinon, réalise d’abord la disposition sans lui demander d’inventer une image de remplacement.

Je veux réaliser l’accueil de mon quiz à partir de la maquette
et du document de design fournis. Lis-les et confirme ce que tu peux consulter.
Si une référence nécessaire est inaccessible, explique ce qui manque.

Objectif : au lancement de l’app, afficher un accueil avec :
- le titre « Mon premier quiz » ;
- la phrase choisie dans mon document ;
- la disposition et les couleurs de ma référence ;
- un bouton « Commencer » qui ouvre le quiz existant.

Garde Kotlin, Compose et l’organisation simple du projet.
Conserve le presenter, les questions, le score, la première réponse définitive
et le comportement de « Question suivante » et « Recommencer ».
Ne refais pas encore le design des questions.
N’ajoute ni bibliothèque, ni connexion, ni nouvelle règle de jeu.
Utilise l’illustration fournie si elle est disponible ; sinon, garde
une version sans illustration et signale-le.

Réalise cette modification limitée. Explique ensuite les fichiers changés,
le lien entre « Commencer » et le quiz, et les vérifications effectuées.
Si une compilation ou une vérification n’a pas été faite, dis-le clairement.
Ne fais ni commit, ni push pour cette étape.

Cette demande prévoit deux moments : l’accueil avant de commencer, puis le quiz existant après le clic. Elle ne demande pas de reconstruire toute l’app à partir de l’image.

Si l’application présente une demande d’autorisation pour un accès ou une commande, lis ce qui est demandé avec l’encadrant. Vérifie son lien avec la tâche avant de décider. Le prompt explique ton intention ; les accès effectifs dépendent aussi de l’environnement.

💡

Périmètre · scope

Ce que la tâche doit couvrir. Ici : l’accueil et son lien vers le quiz existant.

💡

Référence visuelle

Une image qui guide la disposition, les couleurs et les formes. Le bouton doit être construit dans le code pour pouvoir réagir au clic.

💡

Autorisation · permission

Un accès ou une action que l’application demande de permettre. Lis la demande concrète avant de la valider.

05 / Ce qui a changé dans les fichiers

Lis le diff avec l’encadrant.

Quand l’agent termine, ouvre les modifications du projet. Dans Codex, le panneau de revue permet d’examiner les changements d’un dépôt Git. Tu peux aussi les retrouver dans la vue Git d’Android Studio.

Un diff montre la différence entre deux versions. Les lignes marquées - ont été retirées ; celles marquées + ont été ajoutées. Voici un petit exemple illustratif, qui ne décrit pas une modification réelle de ton app :

- Text(text = "Bienvenue")
+ Text(text = "Mon premier quiz")

Ici, le composant reste un Text, mais son texte change. Le panneau peut montrer d’autres modifications : prends le temps de demander à quoi elles servent.

  • Quels fichiers ont changé pour créer l’accueil ?
  • Où est le bouton « Commencer » et quelle action déclenche-t-il ?
  • Les modifications concernent-elles bien l’accueil et son ouverture du quiz ?
  • Les règles du presenter et les données des questions sont-elles conservées ?

Le panneau de revue reflète l’état Git : il peut aussi montrer tes propres modifications, présentes avant le travail de l’agent. Compare avec l’état de départ pour comprendre leur origine.

Explique-moi le changement du bouton Commencer :
quelle fonction reçoit le clic, quelle valeur change,
et pourquoi le quiz devient visible ?
Appuie-toi sur les fichiers modifiés, sans ajouter de nouveau code.

La documentation officielle de revue décrit le panneau de Codex. Pour cette première étape, l’objectif est de comprendre les changements avec l’encadrant, sans apprendre chaque ligne par cœur.

💡

Diff · différence entre versions

Une vue des lignes retirées et ajoutées dans les fichiers. Elle permet d’examiner ce qui change avant de le conserver dans Git.

💡

Review · revue

Une relecture des modifications pour comprendre leur utilité et repérer des problèmes.

06 / Du code écrit à l’app qui fonctionne

Lance et compare à ta référence.

Une réponse « terminé » ne prouve pas que l’écran fonctionne. Lis le compte rendu : l’agent a-t-il compilé le projet, lancé l’app ou seulement modifié les fichiers ? Ce sont des vérifications différentes.

  1. Ouvre le même clone dans Android Studio. Lance l’app avec Run ▶.
  2. Observe l’accueil : textes exacts, lisibilité, couleurs et disposition. Compare à ta référence.
  3. Clique sur « Commencer » : une première question doit apparaître.
  4. Réponds : les choix se désactivent, le message correspond au résultat et le score suit les règles déjà apprises.
  5. Avance jusqu’à la fin, puis utilise « Recommencer ». Vérifie que la nouvelle partie fonctionne toujours.

Si l’agent ne peut pas compiler ou lancer l’app dans son environnement, garde cette limite dans son compte rendu et fais la vérification avec l’encadrant. Compiler ne remplace pas l’observation sur l’appareil.

Une retouche précise

Si le titre est coupé sur l’appareil, donne le résultat observé et, si possible, une capture du problème :

Sur l’appareil, le titre de l’accueil est coupé sur la droite.
Voici la capture et la référence souhaitée.
Corrige la disposition pour afficher le titre entier,
en autorisant plusieurs lignes si nécessaire.
Garde les textes, les couleurs et le comportement du bouton Commencer.
Explique le changement et ce que tu as pu vérifier.

Pour une erreur de compilation ou un crash, fournis le message d’erreur utile et les étapes qui le déclenchent. La méthode d’observation vue avec Logcat sert aussi à guider l’agent.

💡

Compilation · build

La transformation et la vérification du code pour produire une application. Une compilation réussie ne prouve pas à elle seule que tout le parcours fonctionne.

💡

Retouche · refinement

Une nouvelle demande fondée sur un écart observé, avec un changement précis à effectuer.

07 / À toi de guider

Un accueil réalisé, une modification comprise.

  1. Vérifie le dossier Android et l’état Git avec l’encadrant.
  2. Fais expliquer le projet par l’agent, puis fournis tes références d’accueil.
  3. Adapte la demande, fais réaliser l’accueil et relis les changements.
  4. Lance l’app, compare à ta référence et effectue une retouche si nécessaire.
  5. Explique le trajet « clic sur Commencer → changement d’état → affichage du quiz » et ce qui a été vérifié.

Brouillon sans envoi ni sauvegarde. Copie ton compte rendu avant de fermer ou recharger la page.

Mes repères

Confirmations personnelles : le guide ne pilote pas l’agent, ne lit pas le code et ne vérifie pas l’appareil.

Garde ce travail sur ta branche pendant la relecture. Quand la correction est validée avec l’encadrant, retrouve la méthode de commit, push et PR depuis l’IDE. La suite pourra reprendre la même méthode pour réaliser le design de l’écran de question.

💡

Compte rendu

Une trace de ce qui a changé, de ce qui a été observé et de ce qui reste à vérifier. Il aide à poursuivre sans confondre une affirmation et un résultat constaté.

01 / Un outil que tu peux lancer par une commande

Une CLI s’utilise depuis un terminal.

CLI signifie Command Line Interface, « interface en ligne de commande ». Au lieu de commencer par un bouton dans une application, tu écris une commande dans un terminal pour demander du travail à un outil.

Tu connais déjà cette idée avec git status et les commandes Gradle. Codex CLI est l’outil Codex utilisable dans le terminal : il peut examiner le code local, proposer des changements et utiliser les commandes du projet selon les accès disponibles.

Le terminal accueille ces outils. Quand tu démarres Codex, une interface de conversation apparaît à l’intérieur : tu peux alors écrire tes demandes en français, comme avec un agent dans une app desktop.

La CLI change l’interface utilisée pour travailler. Elle ne remplace pas le besoin de donner du contexte, de comprendre les changements et d’observer leur résultat.

💡

Terminal

La fenêtre dans laquelle tu écris des commandes et lis leurs résultats. Plusieurs outils peuvent s’y succéder.

💡

Commande interne · slash command

Une commande de l’interface Codex qui commence par /. Elle n’est pas une commande Git ou une instruction Kotlin.

💡

Session

La conversation en cours avec l’agent, son contexte et ses réglages. Ne suppose pas qu’elle connaît automatiquement tes anciens échanges dans une autre interface.

02 / Une référence et une destination

Retrouve tes deux projets avant de demander le transfert.

Utilise ton clone Android construit pendant le cours, avec sa partie complète. Le dépôt de départ qui ne contient encore que le bouton « Click me » ne peut pas servir de référence pour un quiz terminé.

Le projet Desktop est celui de la page précédente : une fenêtre avec une question et une validation. Les deux versions doivent déjà se lancer avant ce travail, pour distinguer un problème existant d’un effet du transfert.

Quiz Android · référence

Lire les questions, les règles et l’organisation qui existent réellement.

Aucune modification dans ce projet.

StageAcademyDesktop · destination

Reprendre la logique et l’assembler à une interface adaptée à l’ordinateur.

Les changements sont réalisés ici.

  1. Avec l’encadrant, retrouve le chemin complet de chaque dossier sur ton ordinateur. Une adresse GitHub ne désigne pas directement ces fichiers locaux.
  2. Enregistre les fichiers et conserve une version de départ dans Git. Dans un terminal de chaque projet, lis git status et note la branche ainsi que les éventuels changements déjà présents.
  3. Dans Desktop, crée une branche pour le transfert selon notre convention. Par exemple : git switch -c ab/transfer_quiz_logic, en remplaçant ab par tes initiales.
  4. Garde ces chemins et l’état initial à portée de main pour les fournir à Codex.
Le projet Desktop n’est pas encore suivi par Git

Fais préparer avec l’encadrant son historique initial et un gitignore adapté au projet généré, puis vérifiez un premier commit avant la branche de transfert. La page sur le partage depuis l’IDE rappelle les repères de branche, diff et commit. Ne supprime pas de travail pour obtenir un état vide.

Si les projets possèdent déjà des consignes comme AGENTS.md, fais-les repérer. Le rôle « référence Android / destination Desktop » doit rester explicite dans la demande ; une consigne propre à Android peut demander une adaptation dans Desktop.

💡

Chemin complet · absolute path

L’adresse complète d’un dossier sur l’ordinateur, depuis le disque ou la racine du système. Elle dépend de ta machine.

💡

Point de départ Git

Une version enregistrée et un état connus avant la tâche. Ils permettent de relire les changements de l’agent.

03 / Entrer dans le bon dossier

Démarre Codex depuis le projet Desktop.

L’installation et l’accès au compte sont préparés avec l’encadrant. La documentation officielle de Codex CLI donne les méthodes d’installation pour Windows, macOS et Linux. Choisissez celle adaptée à l’ordinateur ; cette page ne l’installe pas.

Dans un terminal normal, vérifie d’abord que la commande est disponible :

codex --version

Un numéro de version doit apparaître. Si la commande est inconnue, fais vérifier l’installation avec l’encadrant ; il peut être nécessaire de rouvrir le terminal après celle-ci.

Remplace CHEMIN_COMPLET_DU_PROJET_DESKTOP par le vrai chemin du dossier. Garde les guillemets, notamment si ce chemin contient des espaces. Les commandes suivantes conviennent dans PowerShell et dans un terminal macOS/Linux :

cd "CHEMIN_COMPLET_DU_PROJET_DESKTOP"
pwd
codex

cd change de dossier ; pwd affiche celui dans lequel tu te trouves. Vérifie le résultat avant de lancer Codex. Au premier démarrage, suis la connexion proposée avec le compte et l’accès préparés par l’encadrant.

Quand la conversation Codex est ouverte, utilise ces commandes internes une à la fois :

/permissions : commencer par lire

Avec l’encadrant, choisis le mode de lecture seule, nommé Read Only dans la documentation. Nous allons d’abord explorer, sans demander de modification. Les options disponibles dépendent de la version et de la configuration.

/status : retrouver le cadre de la session

Lis les réglages et les dossiers autorisés en écriture. Vérifie que la destination de travail est bien Desktop. Ces accès sont des réglages de l’outil ; écrire une consigne dans le prompt ne les configure pas à lui seul.

/quit : revenir au terminal

Quand Codex ne travaille plus, cette commande quitte son interface. Tu retrouves le terminal pour lancer toi-même Git ou Gradle. Les changements déjà écrits dans les fichiers ne sont pas annulés en quittant.

Je ne sais plus si je suis dans le terminal ou dans Codex

Repère l’interface et la zone de saisie. Les phrases destinées à l’agent et les commandes commençant par / se saisissent dans Codex. Pour exécuter toi-même une commande comme git status, utilise un autre terminal ou quitte Codex. Tu peux garder un terminal pour l’agent et un autre pour tes vérifications.

💡

Dossier de travail · working directory

Le dossier depuis lequel on travaille. Ici, il désigne la destination Desktop, pas le clone Android ni le dossier parent des deux projets.

💡

Lecture seule · read only

Un mode prévu pour examiner le projet avant de demander des changements. Les permissions se vérifient dans l’outil avec l’encadrant.

05 / Une demande de réalisation séparée

Fais évoluer le quiz Desktop.

Quand tu comprends la proposition, vérifie avec l’encadrant les permissions nécessaires pour travailler dans Desktop. Utilise /permissions pour permettre les modifications dans cet espace et /status pour relire le cadre. Lis les demandes d’accès ou de commande dans leur contexte.

Envoie ensuite la demande de réalisation dans la même conversation. Adapte-la si tes règles diffèrent de celles du cours :

Réalise le transfert proposé dans le projet Desktop uniquement.
Reprends les vraies questions et les règles du quiz Android :
- une question à la fois, sans passer à la suivante avant une réponse ;
- premier choix définitif, un point si correct, aucun sinon ;
- aucun double comptage et aucune correction du choix après réponse ;
- résultat final et recommencement à la première question avec score à zéro.

Conserve le point d’entrée et la configuration Desktop compatibles.
Adapte la mini-interface existante pour utiliser cette logique,
sans garder un deuxième circuit de validation en parallèle.
Garde des noms anglais, une logique séparée de la vue et les contrats utiles.
Ne reprends pas MainActivity, CameraX, le profil ou son stockage Android.
Préserve les choix de présentation Desktop déjà réalisés quand ils conviennent.

Avance par petites étapes qui compilent. Utilise les tâches Gradle du vrai projet.
Ne modifie pas le projet Android et ne fais pas de commit ou de push.
À la fin, explique les fichiers modifiés, les vérifications exécutées
et ce qui doit encore être observé dans la fenêtre.

Observe les étapes et les messages. Si l’agent propose une modification inattendue, demande-lui son rôle avant de continuer. Tu peux lui demander de reprendre une étape précise plutôt que de lui donner une nouvelle demande générale de refonte.

Résultat attendu : le déroulement de ton quiz dans une fenêtre Desktop.

Le quiz complet remplace l’expérience à une question de la page précédente. Une seule logique de partie doit piloter les réponses et le score.

Pour cette expérience, les données et la logique adaptées sont des copies dans le projet Desktop. Si tu modifies ensuite une question dans Android, elle ne sera pas actualisée automatiquement sur ordinateur. Organiser un module réellement partagé sera une autre étape possible.

Adapter / partager

Adapter une copie permet de découvrir le portage. Partager une même source entre plateformes demande une organisation commune des projets.

06 / Le résultat doit se voir et se relire

Compare les deux quiz, puis garde ton travail.

  1. Dans Codex, utilise /diff pour lire les changements. Retrouve les données, les règles et leur branchement à la vue ; demande une explication d’un passage que tu ne comprends pas.
  2. Dans un terminal Desktop séparé, lis git status et git diff. Pense aussi aux nouveaux fichiers indiqués par status, qui ne sont pas encore suivis.
  3. Dans le clone Android, relis status et diff : compare-les à l’état de départ. Aucun changement de cette tâche ne doit y avoir été ajouté.
  4. Construis Desktop avec la tâche identifiée dans ce projet, puis lance sa fenêtre. Distingue la compilation annoncée par l’agent et le lancement que tu observes.
Vérifications dans la fenêtre Desktop — à adapter à tes questions
SituationCe que tu dois retrouver
Début de partiePremière question, score à zéro, choix activés et suite indisponible avant une réponse.
Une réponse correcteUn seul point, choix désactivés, progression ensuite possible.
Une réponse incorrecteAucun point ; impossible de la remplacer par la bonne réponse sur cette même question.
Fin de partieLes questions se sont succédé dans le bon ordre. Le résultat correspond aux choix faits.
Zéro / toutes / une partie des réponses correctesDes totaux attendus calculés avant la partie, selon le vrai nombre de questions. Aucune règle n’impose de rester à quatre questions.
RecommencerPremière question et score nul, sans état de réponse restant de la partie précédente.

Compare aussi les énoncés et les choix avec Android. Pour ce transfert de logique, les fenêtres n’ont pas à être visuellement identiques. Vérifie toutefois que les textes longs, les boutons et le résultat restent accessibles en redimensionnant la fenêtre.

Après relecture et observations avec l’encadrant, fais un commit des changements Desktop utiles, selon la méthode déjà apprise. Un message possible est [DesktopQuiz] Transfer quiz rules from Android. Si tu veux ensuite partager ton projet, vérifie sa destination GitHub avant de pousser.

« Tout fonctionne » dans la réponse de l’agent suffit-il ?

Demande quelles commandes ont été exécutées et quels comportements ont réellement été observés. Une compilation réussie ne prouve pas que le score ou le recommencement fonctionne dans la fenêtre. Note les cas que tu n’as pas encore reproduits.

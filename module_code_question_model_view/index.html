01 / Lire ce qui se répète

Quelles informations décrivent une question ?

Tu retrouves trois rôles pour chaque question : le texte de l’énoncé, la liste des choix et la bonne réponse. Les préfixes firstQuestion et secondQuestion t’aident à les relier, mais ce lien existe seulement dans leurs noms.

Nous voulons transmettre une question complète à l’affichage, sans donner séparément chaque information. Imagine une fiche avec trois champs toujours présents.

text · String
L’énoncé de la question.
choices · List<String>
Ses choix, dans l’ordre.
correctAnswer · String
Sa bonne réponse.

Avec l’encadrant, garde d’abord la version à deux questions qui fonctionne dans Git, puis prépare une branche de travail comme ab/modeliser_les_questions.

💡

Modèle de données · data model

Une description des informations qui constituent quelque chose. Ici, les trois champs d’une question.

💡

Champ / propriété · property

Une information nommée qui appartient à un objet. Le texte d’une question sera une propriété de cet objet.

02 / Décrire la forme commune

Ta première data class.

Une classe définit un type que l’on peut utiliser dans le programme. Une classe peut réunir des données et des actions. Pour commencer, notre classe Question décrit uniquement des données :

data class Question(
    val text: String,
    val choices: List<String>,
    val correctAnswer: String,
)

class Question donne un nom au modèle. Le mot-clé data indique que cette classe sert principalement à représenter des données. Les trois propriétés et leurs types sont déclarés entre parenthèses.

Les val font ici partie de la classe : chaque question créée possédera ses propres valeurs pour text, choices et correctAnswer. Déclarer ce modèle ne crée pas encore de question concrète.

Place la définition au niveau du fichier, en dehors de WelcomeScreen et des autres fonctions. Nous n’ajoutons pas de nouveau fichier ni de nouvelle architecture à ce stade.

💡

Classe · class

Un modèle qui définit un type et ce que ses objets possèdent. Ici, Question décrit les données communes à toutes nos questions.

💡

Data class

Une classe Kotlin destinée à représenter des données. Nous commençons par ses propriétés ; ses autres possibilités viendront quand elles seront utiles.

💡

Question / question

Une majuscule commence le nom de la classe Question. Une variable qui contient une question garde une minuscule : question, firstQuestion.

03 / Remplir la fiche

Crée deux instances du même modèle.

Une instance est un objet concret créé à partir d’une classe. Voici notre première question :

val firstQuestion: Question = Question(
    text = "Quel outil garde l’historique du code ?",
    choices = listOf("Git", "Android", "Compose"),
    correctAnswer = "Git",
)

firstQuestion: Question indique le nom et le type de notre variable. À droite, Question(…) crée un objet avec les valeurs fournies. Nous nommons les arguments pour lire facilement ce que nous donnons à chaque propriété.

Ce text = … ne déclare pas une nouvelle variable locale : il indique la valeur transmise au paramètre text lors de la création de l’objet.

Le même modèle permet de créer la deuxième question :

val secondQuestion: Question = Question(
    text = "Quel composant Compose affiche du texte ?",
    choices = listOf("Button", "Text", "Column"),
    correctAnswer = "Text",
)

Reporte dans choices les choix que tu as conservés à la page précédente, y compris « Logcat » si tu l’as ajouté, et leur ordre. Les trois choix du bloc fourni sont un exemple de référence, pas une consigne pour retirer les tiens. Garde aussi ton énoncé et sa bonne réponse.

Les objets ont la même forme, mais des contenus différents. La première question attend « Git », la deuxième attend « Text ».

Comment lire une information dans une question ?
val questionText: String = firstQuestion.text
val choices: List<String> = firstQuestion.choices
val correctAnswer: String = firstQuestion.correctAnswer

Le point permet de lire une propriété de cet objet. firstQuestion.correctAnswer vaut « Git » ; secondQuestion.correctAnswer vaut « Text ».

La classe garantit-elle que la bonne réponse figure dans les choix ?

Pas avec cette définition. Elle exige les trois propriétés et leurs types, mais tu dois encore fournir des données cohérentes. Vérifie que la bonne réponse correspond exactement à un choix. Nous ajouterons des règles supplémentaires quand le quiz en aura besoin.

💡

Objet / instance · object / instance

Une réalisation concrète d’une classe. firstQuestion et secondQuestion désignent ici deux objets Question.

💡

Constructeur · constructor

Ce qui permet de créer une instance avec ses informations de départ. En Kotlin, nous l’appelons ici avec Question(…).

04 / Réutiliser la liste

Une liste peut contenir des questions.

Tu connais List<String>. Le même principe permet de regrouper nos objets :

val questions: List<Question> = listOf(firstQuestion, secondQuestion)

Chaque élément est maintenant une Question. Pendant le parcours, le nom local question désigne successivement chacun de ces objets :

for (question: Question in questions) {
    QuestionView(question = question)
}

Nous allons définir QuestionView pour afficher la question reçue. Le parcours ne connaît plus les noms firstQuestionText ou secondQuestionChoices : il transmet chaque objet complet à la même vue.

Deux niveaux de listes, deux rôles.

questions regroupe les questions du quiz. question.choices regroupe les choix d’une question précise. La première contient des Question, la seconde des String.

💡

List<Question>

Une liste dont les éléments sont des objets Question. La liste conserve l’ordre dans lequel nous les affichons.

💡

Argument nommé

Dans QuestionView(question = question), le nom à gauche du signe = désigne le paramètre ; à droite, on transmet la valeur locale question.

05 / Une fonction pour le même affichage

QuestionView reçoit une question.

Les deux groupes de boutons avaient la même forme. Une fonction d’interface peut décrire ce groupe une seule fois, puis recevoir la question à afficher :

@Composable
fun QuestionView(question: Question) {
    var feedbackText: String by remember(question) {
        mutableStateOf("Choisis une réponse.")
    }

    fun checkAnswer(selectedAnswer: String): Unit {
        val isAnswerCorrect: Boolean = isCorrectAnswer(
            selectedAnswer,
            question.correctAnswer,
        )
        if (isAnswerCorrect) {
            feedbackText = "Bonne réponse !"
        } else {
            feedbackText = "Essaie encore."
        }
    }

    Column(
        verticalArrangement = Arrangement.spacedBy(12.dp),
        horizontalAlignment = Alignment.CenterHorizontally,
    ) {
        Text(text = question.text)
        for (choice: String in question.choices) {
            Button(onClick = { checkAnswer(choice) }) {
                Text(text = choice)
            }
        }
        Text(text = feedbackText)
    }
}

question.text fournit l’énoncé. La boucle lit question.choices. Au clic, la validation reçoit question.correctAnswer. Ces informations restent réunies dans le même objet.

Chaque appel de QuestionView possède son état d’affichage pour le message. Le cadre remember(question) conserve cet état pendant les mises à jour de la même vue ; si la question reçue change, il repart du message initial. Nous gardons ici un ordre fixe des questions, sans réorganisation pendant l’exécution.

La fonction locale checkAnswer est décrite une seule fois dans la vue, au lieu d’écrire checkFirstAnswer et checkSecondAnswer. Elle travaille avec la question reçue par cet appel. La règle isCorrectAnswer reste la même fonction Kotlin indépendante.

💡

QuestionView · vue d’une question

Une fonction Compose réutilisable. Elle reçoit les données d’une question et décrit ses textes, ses boutons et son message.

💡

Données et affichage

Question décrit les informations. QuestionView décrit leur affichage et relie les clics à la validation. Le message affiché appartient encore à la vue dans cette étape.

  3. Remplace uniquement la fonction WelcomeScreen et sa ligne @Composable par l’exemple ci-dessous. Il crée les données puis appelle QuestionView pour chaque question.

Le nouveau WelcomeScreen complet
@Composable
fun WelcomeScreen(modifier: Modifier = Modifier) {
    val firstQuestion: Question = Question(
        text = "Quel outil garde l’historique du code ?",
        choices = listOf("Git", "Android", "Compose"),
        correctAnswer = "Git",
    )

    val secondQuestion: Question = Question(
        text = "Quel composant Compose affiche du texte ?",
        choices = listOf("Button", "Text", "Column"),
        correctAnswer = "Text",
    )

    val questions: List<Question> = listOf(firstQuestion, secondQuestion)

    Column(
        modifier = modifier
            .fillMaxSize()
            .verticalScroll(rememberScrollState())
            .padding(24.dp),
        verticalArrangement = Arrangement.spacedBy(24.dp),
        horizontalAlignment = Alignment.CenterHorizontally,
    ) {
        Text(
            text = stringResource(R.string.welcome_title),
            style = MaterialTheme.typography.headlineMedium,
        )
        for (question: Question in questions) {
            QuestionView(question = question)
        }
    }
}

Aucun nouvel import n’est nécessaire par rapport à la page précédente. Le défilement reste sur l’écran qui contient toutes les questions. Les blocs de données et d’actions de l’ancien WelcomeScreen sont remplacés, pas conservés en double.

Qu’est-ce qui a été déplacé ?

L’énoncé, les choix et la réponse sont les propriétés d’un objet Question. Les deux affichages sont remplacés par un seul QuestionView appelé deux fois. Les messages et l’action locale sont maintenant dans cette vue. Tout reste dans le même fichier et la règle de validation ne change pas.

Question : faut-il une nouvelle classe pour chaque question ?

Non. Les questions partagent la même description, la classe Question. Nous créons plusieurs instances avec des valeurs différentes. Une classe pour chaque énoncé ferait perdre l’intérêt du modèle commun.

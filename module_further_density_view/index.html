01 / Plus de pixels dans un même espace

Densité et taille d’écran sont deux choses différentes.

Deux écrans de taille proche peuvent contenir un nombre différent de pixels. La densité décrit la quantité de pixels dans un espace physique donné.

Schéma HTML/CSS : les cadres ont la même taille et les grilles représentent deux densités. Ce ne sont pas des captures d’appareils ni une mesure de ton écran.

Dans le fichier, nous comptons des pixels, ou px. Pour une dimension de l’interface Android, tu utilises déjà les dp, des unités indépendantes de la densité. Android les traduit en pixels adaptés à l’écran.

Dans notre exemple, l’illustration occupe un cadre de 96.dp. Elle peut demander 96 pixels de côté sur une densité de référence et davantage sur une densité plus élevée.

Le cadre reste de 96 dp ; le fichier adapté peut contenir plus de pixels.

On cherche une image assez détaillée pour ce cadre, pas une illustration quatre fois plus grande à l’écran.

💡

Densité · density

Le nombre de pixels dans un espace donné. Ce n’est pas simplement la largeur de l’écran.

💡

dp

Density-independent pixel : une unité de dimension de l’interface Android, distincte des pixels du fichier image.

02 / Cinq fichiers, un seul nom de ressource

Le dossier précise la densité.

Android reconnaît des groupes de densité. Pour notre illustration carrée de 96 dp, préparons les cinq variantes suivantes :

Le fichier portera partout le nom quiz_illustration.png. Dans le code, une seule référence, R.drawable.quiz_illustration, désigne la ressource. Android sélectionne une variante selon la configuration et peut ajuster son échelle.

Ces nombres sont liés à notre choix de 96 dp. Ils ne sont pas les dimensions universelles d’une image Android. D’autres groupes existent, comme ldpi et tvdpi ; cette première génération se limite aux cinq variantes du tableau.

Faut-il créer cinq PNG pour chaque image de l’app ?

Non. L’exercice concerne une illustration bitmap intégrée à l’accueil. Une icône vectorielle Android peut s’adapter à plusieurs densités sans ces cinq PNG. La photo du profil créée pendant l’usage reste un fichier chargé par l’app, pas une ressource générée dans res.

Les icônes de lancement utilisent les dossiers mipmap et d’autres règles ; ne remplace pas ces icônes ici. Un dossier drawable-nodpi sert à un autre choix de mise à l’échelle et ne remplace pas nos variantes pour cette expérience.

💡

Bitmap

Une image décrite par ses pixels, comme notre PNG. Une image vectorielle décrit plutôt des formes et des tracés.

💡

Qualificatif · qualifier

Une précision dans le nom du dossier de ressources. Ici, le suffixe -xhdpi précise une densité.

03 / Réutiliser ton premier outil

Un script organise cinq redimensionnements.

Reprends une source PNG carrée d’au moins 384 × 384 px, idéalement ton original de 512 × 512 px ou plus. Ne pars pas de la copie réduite à 256 px : elle n’a plus assez de pixels pour notre plus grande variante.

Dans quiz_image_tool, conserve resize_image.py de la page précédente et ajoute generate_android_images.py. Les deux scripts doivent être côte à côte :

quiz_image_tool/
├── resize_image.py
├── generate_android_images.py
└── source.png
Le nouveau script complet fourni
# /// script
# requires-python = ">=3.11"
# dependencies = ["pillow>=11,<14"]
# ///

import argparse
from pathlib import Path

from PIL import Image
from resize_image import resize_image


def generate_android_images(source_path: Path, output_dir: Path) -> None:
    density_sizes: dict[str, int] = {
        "mdpi": 96,
        "hdpi": 144,
        "xhdpi": 192,
        "xxhdpi": 288,
        "xxxhdpi": 384,
    }

    with Image.open(source_path) as source_image:
        if source_image.format != "PNG":
            raise ValueError("Pour cet exercice, utilise une vraie image PNG.")
        if source_image.width != source_image.height:
            raise ValueError("La source doit être carrée pour notre illustration de 96 dp.")
        if source_image.width < 384:
            raise ValueError("La source doit mesurer au moins 384 x 384 pixels.")

    output_dir.mkdir(parents=True, exist_ok=False)
    for density, size in density_sizes.items():
        output_path: Path = output_dir / f"drawable-{density}" / "quiz_illustration.png"
        resize_image(source_path, output_path, size)

    print(f"Cinq variantes créées dans : {output_dir.resolve()}")


def main() -> None:
    parser = argparse.ArgumentParser(
        description="Préparer les cinq variantes Android d’une illustration carrée de 96 dp."
    )
    parser.add_argument("source", type=Path, help="Source PNG carrée, au moins 384 x 384 px")
    parser.add_argument("output_dir", type=Path, help="Nouveau dossier de sortie")
    args = parser.parse_args()

    if args.output_dir.exists():
        parser.error("La sortie existe déjà. Choisis un nouveau dossier.")
    try:
        generate_android_images(args.source, args.output_dir)
    except (OSError, ValueError) as error:
        parser.exit(1, f"Impossible de préparer les ressources : {error}\n")


if __name__ == "__main__":
    main()

from resize_image import resize_image reprend la fonction de ton premier fichier. Son bloc de démarrage ne s’exécute pas quand on l’importe : ici, nous voulons sa fonction, pas lancer son ancienne commande.

density_sizes associe chaque nom de densité à sa taille. C’est un dictionnaire Python. La boucle parcourt ces associations et appelle cinq fois la même action, chaque fois avec un dossier et une taille différents. Chaque variante repart de la source originale, pas de la variante réduite juste avant.

Dans le terminal placé dans quiz_image_tool, lance :

uv run generate_android_images.py "source.png" "generated_res"

Le nouveau script déclare aussi Pillow pour qu’uv prépare son environnement. Il vérifie le format, la forme carrée et la taille avant de créer les sorties. Un dossier de destination déjà présent est refusé : utilise un nouveau nom pour refaire un essai.

generated_res/
├── drawable-mdpi/quiz_illustration.png
├── drawable-hdpi/quiz_illustration.png
├── drawable-xhdpi/quiz_illustration.png
├── drawable-xxhdpi/quiz_illustration.png
└── drawable-xxxhdpi/quiz_illustration.png

Vérifie les cinq fichiers et leurs dimensions avant de les intégrer. Une interruption ou une erreur d’écriture peut laisser une sortie partielle : le dossier seul ne prouve pas que la génération est terminée.

💡

Dictionnaire · dictionary

Une collection d’associations entre une clé et une valeur. Ici : le nom de densité et la taille correspondante.

💡

Génération par lot · batch

Le même travail appliqué à plusieurs sorties. Les règles sont décrites une fois, puis la boucle les répète.

04 / Utiliser ce que ton outil a produit

Ajoute les variantes à l’accueil du quiz.

  1. Dans ton clone Android, retrouve app/src/main/res/. Copie les cinq dossiers drawable-* depuis generated_res vers ce dossier.
  2. Si un dossier existe déjà, ajoute le fichier à son contenu sans remplacer ses autres ressources. Si quiz_illustration existe déjà dans le projet, fais examiner ce cas avec l’encadrant avant d’écraser quoi que ce soit.
  3. Vérifie que chaque dossier contient quiz_illustration.png. Ne copie ni le dossier generated_res lui-même sous res, ni la grande source de travail dans drawable par défaut.
  4. Dans le composable de ton accueil Android, ajoute le bloc fourni après le titre, ou adapte l’illustration existante à cette ressource. Garde le reste du design et les règles du quiz.

Ce bloc va à l’intérieur du composable de l’accueil, pas au niveau du fichier. L’import R correspond au namespace du quiz du cours ; adapte-le si ton projet utilise un autre namespace.

L’illustration est ici décorative, accompagnée du titre du quiz : la description vaut null. Si ton image transmet une information utile, donne-lui une description accessible adaptée, comme à la page sur l’affichage des images.

Construis puis lance l’app. Le même code garde un cadre de 96 dp : il n’a pas à contenir cinq chemins ou une condition sur la densité. Ces dossiers sont des ressources Android ; le projet Desktop n’utilise pas automatiquement cette organisation.

R.drawable

Les identifiants générés pour retrouver les ressources graphiques Android. L’extension .png ne figure pas dans l’identifiant.

💡

Ressource intégrée

Un fichier ajouté au projet et livré dans l’application. Il est distinct d’une photo créée pendant l’utilisation.

05 / Une autre façon de réaliser la même opération

Une bibliothèque Python ou un outil en CLI.

Avec Pillow, Python appelle directement des fonctions de bibliothèque. ImageMagick propose aussi le traitement d’image comme outil en ligne de commande. Si l’encadrant l’a installé, tu peux essayer cette variante facultative depuis le dossier de travail :

magick "source.png" -resize "96x96>" "magick_96.png"

Le résultat tient dans 96 × 96 pixels en gardant les proportions. Le signe > signifie ici « réduire seulement » ; les guillemets font partie de la commande, pour que le terminal ne traite pas ce signe autrement.

Choisis un nom de sortie encore libre : cette commande ne reprend pas les refus de réécriture de notre script Python. Pour une source carrée suffisante, compare ses dimensions à la variante mdpi de Pillow ; les fichiers n’ont pas besoin d’être identiques octet par octet.

Comment Python pourrait-il piloter ImageMagick ?

Python peut lancer un programme externe avec le module standard subprocess. Un autre script pourrait organiser les mêmes cinq commandes et vérifier leurs résultats. Ce serait une alternative au traitement Pillow, à préparer séparément avec l’agent ; ne lance pas les deux approches vers les mêmes fichiers.

uv prépare les dépendances Python déclarées, mais n’installe pas à lui seul la commande magick. Cette première génération fonctionne entièrement avec Pillow ; ImageMagick n’est pas un prérequis.

💡

Outil externe

Un autre programme que le script peut appeler. Ses besoins d’installation restent distincts des paquets Python.

06 / Un outil dont tu peux expliquer les règles

Vérifie les fichiers, puis l’application.

  1. Avant la génération, annonce les cinq tailles attendues pour le cadre de 96 dp. Après, retrouve-les dans les propriétés des fichiers.
  2. Compare l’original et les variantes : la source doit être conservée, l’image carrée et ses proportions inchangées.
  3. Avec une source trop petite ou rectangulaire, observe le refus et explique pourquoi le premier script acceptait ces images alors que cet exercice impose un autre contrat.
  4. Dans l’app, vérifie l’illustration d’accueil et lance une partie : les questions, le score et le recommencement restent ceux d’avant.
  5. Avec l’encadrant, si deux appareils ou émulateurs de densités différentes sont disponibles, compare le cadre affiché et la netteté. Un redimensionnement de fenêtre ou une taille d’écran différente ne prouve pas à lui seul une autre densité. Laisse ce point non vérifié si tu n’as qu’une configuration.
  6. Relis le diff Git : cinq ressources et l’affichage ciblé, puis conserve les changements après vérification. Les scripts et la source de travail restent hors de res.
Pourquoi refuser une source plus petite que 384 pixels ?

Le premier outil ne l’agrandit pas. Sans cette vérification, un fichier pourrait être placé dans drawable-xxxhdpi alors qu’il ne contient pas les 384 × 384 pixels attendus. Agrandir une petite image n’invente pas les détails manquants.

Comment faire évoluer cet outil avec l’agent ?

Demande-lui d’abord de retrouver la table des tailles, la boucle et l’appel à resize_image. Il pourra ensuite proposer un paramètre pour une autre taille en dp. Fais calculer les nouvelles dimensions attendues avant toute modification et conserve une source assez grande.

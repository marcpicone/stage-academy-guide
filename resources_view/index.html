01 / Choisir ce qui aide pour la tâche

Une consigne durable et une procédure ont des rôles différents.

Le fichier de consignes du projet

Il explique le projet et ses habitudes : règles du quiz, noms, organisation et vérifications. Ces repères servent à plusieurs demandes.

Un skill

Une procédure réutilisable pour un travail précis, par exemple relire une modification. Son fichier SKILL.md décrit quand l’utiliser et comment mener ce travail.

Les réglages de l’outil

Ils définissent notamment des accès et des préférences. Les kits ne changent pas ces réglages. Un texte Markdown ne configure pas à lui seul les permissions de l’agent.

Voici les conventions choisies pour les deux kits de cette page. Les noms exacts comptent :

Pour notre kit Codex, c’est AGENTS.md au pluriel et .agents avec un point. Un fichier nommé agent.md ou un dossier .agent créé librement ne reproduit pas ces emplacements.

Claude Code peut-il aussi lire AGENTS.md ?

Des versions récentes le permettent selon leurs réglages. Le kit Claude fournit ici un CLAUDE.md autonome pour garder un point de départ explicite. Consulte la documentation de ta version et vérifie les consignes effectivement chargées. Si tu utilises les deux fichiers dans un même projet, garde leurs décisions cohérentes.

03 / Savoir expliquer ce qu’on donne à l’agent

Les modèles décrivent le quiz et ses règles.

Les deux fichiers de consignes proposent le contenu suivant. Tu peux le lire ici avant de télécharger :

Lire le modèle de consignes
# Consignes du quiz

## Projet

Ce modèle décrit le quiz Android du parcours Stage Academy : Kotlin, Compose
et un module app. Avant de l’utiliser, confirme la cible et les noms réels du
projet. Pour le compagnon Desktop, adapte ce paragraphe et les commandes Gradle.

Lis le code et les consignes existantes avant une modification. Les données
d’une question, les règles du presenter et l’affichage ont des rôles distincts.
Conserve l’organisation réellement présente ; nos packages de vue portent le
suffixe _view. Les modèles de données restent distincts des vues.

## Règles de la partie

- Afficher une question à la fois et attendre une réponse avant la suivante.
- Garder le premier choix définitif : un point si correct, aucun sinon.
- Empêcher le double comptage et le remplacement du choix après validation.
- Afficher le résultat selon le vrai nombre de questions, sans supposer quatre.
- Recommencer à la première question avec le score et l’état de réponse remis à zéro.

Si la demande change une règle, explique son effet et adapte les comportements
concernés. Pour un changement de présentation, garde les règles en place.

## Manière de travailler

- Utilise des identifiants anglais et des textes d’interface français.
- Garde les changements liés au besoin demandé et explique les nouveaux concepts.
- Vérifie les dépendances et les commandes dans le projet réel avant de les utiliser.
- Pour un transfert entre projets, distingue la référence à lire et la destination à modifier.

## Vérification et compte rendu

Utilise le Gradle Wrapper du projet pour les tâches adaptées. Dans le quiz Android
simple, :app:assembleDebug produit l’APK debug. Une compilation ne prouve pas le
fonctionnement sur appareil.

Pour une modification des règles, vérifie ou propose l’observation des scores
zéro/toutes/une partie des bonnes réponses, du premier choix définitif et du
recommencement. Pour la vue, examine aussi les textes longs et l’espace disponible.

Explique ce qui a changé et pourquoi, les commandes réellement exécutées et leurs
résultats, ainsi que les observations restantes. Les commits, push et PR suivent
la demande de publication ; écrire ces consignes ne publie rien.

Le début situe la cible et l’organisation ; la suite rend visibles les règles du jeu et les vérifications attendues. Ce texte doit décrire ton projet réel. S’il n’utilise plus les mêmes noms ou si une règle a été changée volontairement, adapte le modèle.

Écrire « un point si correct » ne réalise pas le calcul dans Kotlin. Cela guide le travail de l’agent ; le comportement reste à lire et à vérifier dans l’application.

💡

Markdown · .md

Du texte avec quelques signes de mise en forme : # pour un titre, - pour une liste. Les consignes restent lisibles dans un éditeur.

💡

Modèle · template

Un point de départ à adapter. Ce n’est pas une description vérifiée automatiquement de ton clone.

04 / Deux procédures courtes

Choisis un skill pour un besoin précis.

review-quiz-change · relire une modification

Il fait suivre les changements de la réponse à la progression, au score et à la vue. Il demande des défauts étayés, des scénarios concrets et une distinction entre vérifications réalisées et proposées. C’est une revue sans modification du code.

name: review-quiz-change

---

# Relire une modification du quiz

Lis les consignes du projet, son état Git et les changements concernés par la
demande, y compris le contenu des nouveaux fichiers. Utilise le code environnant
pour comprendre l’effet réel d’un changement ; n’invente pas un problème à partir
du seul nom d’un fichier.

Suivant le périmètre modifié, suis le trajet du clic à la validation, au score
et à l’état relu par la vue. Recherche notamment :

- une progression possible sans réponse ou une lecture de question après la fin ;
- un deuxième comptage, un premier choix remplaçable ou un total fixé à quatre ;
- un recommencement qui garde l’indice, le score ou l’état d’une ancienne réponse ;
- une vue qui ne relit plus l’état ou masque une action avec un texte long.

Pour chaque défaut étayé, donne le fichier et l’endroit, un scénario concret,
l’effet observé dans le code et une correction suggérée. Distingue une régression
d’une préférence de style. Si tu ne trouves pas de défaut étayé, indique-le.

Propose les commandes et les observations utiles pour les incertitudes restantes.
Présente ces propositions comme non exécutées. Cette revue ne modifie pas les
fichiers et ne crée ni commit ni publication.

add-quiz-question · ajouter une question

Il fait retrouver le format actuel des données, ajouter une question avec ses choix et sa bonne réponse, puis vérifier le nombre de questions et le déroulement. Il conserve les règles de score et l’interface existante autant que possible.

# Ajouter une question au quiz

Lis les consignes et retrouve l’endroit où les questions sont réellement définies.
Examine une question existante et les règles qui consomment ces données avant
d’ajouter quoi que ce soit. Respecte le modèle déjà en place.

Reprends l’énoncé, les choix et la bonne réponse demandés. S’il manque une
information, distingue ta proposition du contenu fourni et fais préciser ce qui
est nécessaire pour obtenir une question sans ambiguïté.

Ajoute la question dans les données. Garde des noms de code anglais et des textes
français. Vérifie que la bonne réponse correspond à un des choix et que les choix
permettent une réponse claire. Conserve la logique de progression et de score ;
l’ajout d’une question ne doit pas imposer une copie de l’interface.

Repère les textes ou calculs qui supposeraient un ancien nombre de questions et
adapte seulement ce qui est nécessaire à la demande. Explique toute adaptation
qui dépasse l’ajout de données.

Utilise la tâche de construction adaptée au projet si l’environnement le permet.
Indique son résultat réel. Fais observer ou propose de vérifier la nouvelle
question, ses choix, la fin de partie et le recommencement ; ne déclare pas un
scénario validé sans l’avoir exécuté. Termine par les fichiers changés, la raison
des changements et les vérifications restantes. Les actions Git de publication
restent celles demandées par l’utilisateur.

Pour un téléchargement individuel, crée le dossier du skill dans .agents/skills ou .claude/skills selon ton outil, puis renomme le fichier téléchargé en SKILL.md. Les deux skills ont chacun leur propre dossier ; ne les rassemble pas dans un unique fichier.

L’en-tête entre les lignes --- contient un nom et une description. La description aide l’agent à reconnaître les demandes concernées. Le reste du fichier décrit la procédure.

💡

Revue · review

Relire un changement pour comprendre son effet et repérer un problème. Une proposition de vérification n’est pas une vérification exécutée.

💡

Métadonnées

Des informations qui décrivent le fichier. Ici, name et description identifient le skill et son usage.

05 / Faire correspondre le texte au code

Adapte le modèle au projet choisi.

  1. Choisis le projet concerné : quiz Android ou compagnon Desktop. Les consignes se placent dans ce projet, pas dans le dossier parent des deux.
  2. Relis le fichier existant s’il y en a un, puis adapte le contexte, les noms et les règles réellement conservées.
  3. Pour Desktop, remplace la présentation Android et le module app par la cible Desktop réelle. Retrouve sa commande Gradle ; ne conserve pas :app:assembleDebug comme commande de construction Desktop.
  4. Vérifie les chemins des skills et garde les permissions dans les réglages de l’outil, distincts de ces modèles.
  5. Relis le diff Git et conserve les fichiers de consignes utiles avec le projet après validation avec l’encadrant.

Si le travail utilise un projet comme référence et un autre comme destination, rappelle ces rôles dans la demande du moment. Une instruction durable ne remplace pas le contexte précis d’un transfert.

Ces kits ne contiennent ni configuration de modèle, ni connexion à un service, ni commande d’installation. Tu peux commencer par le seul fichier de consignes et ajouter un skill lorsqu’un besoin se répète.

06 / Vérifier la prise en compte

Fais retrouver les fichiers dans une session du projet.

Ouvre une nouvelle session de l’agent dans le projet choisi. Demande-lui de lire le fichier de consignes et d’expliquer trois règles sans modifier de fichier. Compare sa réponse au contenu que tu as installé.

Pour les skills, vérifie leur présence dans l’interface de ton outil. Dans Codex CLI, tu peux ouvrir /skills ou mentionner un skill avec $. Dans Claude Code, les skills de projet peuvent être invoqués par leur nom précédé de /. Les exemples suivants se saisissent dans la conversation de l’agent, pas comme des commandes du terminal :

Codex

$review-quiz-change Relis mes changements locaux sans modifier de fichier.

Claude Code

/review-quiz-change Relis mes changements locaux sans modifier de fichier.

Pour essayer l’ajout de question, prépare les données complètes. Par exemple : énoncé « Quel mot-clé déclare une fonction en Kotlin ? », choix « fun », « val », « class », bonne réponse « fun ». Utilise add-quiz-question seulement lorsque tu souhaites réellement cet ajout, puis relis et vérifie le résultat.

Le skill n’apparaît pas ou l’agent ne retrouve pas les consignes

Vérifie le dossier depuis lequel tu as ouvert l’agent, les noms exacts, l’emplacement des fichiers et l’absence d’une extension .txt ajoutée par l’éditeur. Consulte les règles de découverte de ta version et relance la session si nécessaire. La présence d’un ZIP dans le dossier Téléchargements ne signifie pas que le kit est installé.

Les fichiers ont été préparés pour le cours. Leur validation de format ne prouve ni leur chargement dans ton installation ni la qualité de chaque réponse de l’agent. Le guide ne consulte pas ton projet et n’enregistre aucune progression.

01 / Le même projet, deux interfaces

Vérifie ton point de départ.

Dans Android Studio, ouvre le clone de ton fork. La page précédente doit être terminée : tu as remplacé 0 par 4 dans MainActivity.kt, relancé et vu « 25 points par question » sans crash.

Ta correction est encore locale et non commitée. La branche courante doit être dev. Nous créons maintenant une branche pour y conserver ce travail. Pour les prochaines modifications, prends l’habitude de créer la branche avant de coder.

- val nombreDeQuestions = 0
+ val nombreDeQuestions = 4

Diff illustratif : la ligne avec « − » est retirée, celle avec « + » la remplace. Les signes ne font pas partie du code Kotlin.

Choisis un seul chemin pour faire l’exercice.

La vue Git et le terminal pilotent le même dépôt : ce que tu fais dans l’un apparaît dans l’autre. Tu peux lire les deux parcours, mais ne crée pas deux branches ou deux commits pour cette correction.

Nous utiliserons l’exemple ab/corriger_calcul_score. Remplace ab par tes initiales dans les boutons comme dans les commandes. Le message sera [QuizScore] Corrige le calcul des points par question.

Je suis déjà sur une autre branche, ou je vois d’autres changements

Montre l’état à l’encadrant avant de continuer. Ne supprime aucun fichier pour obtenir le même affichage que le cours. Si la correction est déjà commitée ou poussée, retrouvez ensemble l’étape atteinte et reprenez à partir de là.

💡

Fork / origin

Ton fork est ta copie du dépôt sur GitHub. origin est le nom donné ici à l’adresse distante utilisée pour envoyer ton travail. Cette adresse doit viser ton compte.

💡

Branche · branch

Une ligne de travail nommée dans l’historique Git. Notre convention est initiales/nom_de_branche ; c’est un choix d’équipe.

💡

Diff · différences

La comparaison entre deux versions d’un fichier. Elle permet de relire exactement les changements à enregistrer.

02 / Deux façons de faire

Depuis les boutons ou le terminal.

Ouvre le parcours que tu souhaites suivre. Dans les deux cas, relis la destination et le changement avant d’envoyer ton travail.

Chemin A · La vue Git d’Android Studio

1. Vérifier le dépôt distant

Ouvre Git → Manage Remotes… (gérer les dépôts distants). Vérifie que origin pointe vers https://github.com/TON_PSEUDO/stage_academy.git, ou son équivalent SSH si préparé avec l’encadrant. Il doit viser ton compte, pas marcpicone. Ferme cette fenêtre sans changer l’adresse si elle est correcte.

2. Créer ta branche

Clique sur le nom de la branche courante dans la barre d’outils, ou ouvre Git → Branches. Depuis dev, choisis New Branch (nouvelle branche), saisis ab/corriger_calcul_score avec tes initiales, puis active-la avec Checkout si proposé. Vérifie que ce nouveau nom est maintenant affiché. La modification non commitée reste avec toi.

3. Lire et sélectionner le changement

Ouvre la fenêtre Commit via View → Tool Windows → Commit, ou l’action Git → Commit…. Selon la version et les réglages, les changements peuvent aussi apparaître dans Git → Local Changes (changements locaux).

Ouvre le diff de MainActivity.kt. Retrouve le passage de 0 à 4. Sélectionne uniquement ce fichier. Si l’IDE utilise une zone Staged (préparé), ajoute ce fichier à cette zone ; sinon, coche-le dans la liste du commit.

4. Créer le commit local

Saisis [QuizScore] Corrige le calcul des points par question, puis choisis Commit. Pour bien distinguer les étapes, garde le push pour la suivante. Si l’IDE te demande une identité Git, ouvre l’aide « identité » après le parcours B et renseigne-la avec l’encadrant.

Vérifie dans l’historique Git, onglet Log, que le message apparaît sur ta branche. Le fichier ne doit plus avoir de changement en attente pour cette correction.

5. Pousser la branche

Ouvre Git → Push…. Vérifie l’envoi de ta branche vers origin, avec le même nom de branche distante. Lis les commits proposés puis clique sur Push. Attends le résultat de l’envoi avant de passer à la PR.

Les menus dépendent de la version d’Android Studio et de son intégration Git. Si un intitulé diffère, retrouve l’action avec l’encadrant ou utilise le chemin terminal à partir de l’étape déjà atteinte.

Chemin B · Le terminal intégré d’Android Studio

Ouvre View → Tool Windows → Terminal. Utilise le terminal préparé avec l’encadrant, par exemple Git Bash sous Windows. Exécute les commandes une par une, dans le dossier stage_academy.

1. Vérifier où tu travailles

git status
git remote -v

status doit indiquer la branche dev et MainActivity.kt modifié. remote -v affiche les adresses distantes : celles d’origin doivent viser ton fork. Si ce n’est pas le cas, arrête-toi avec l’encadrant pour retrouver le bon clone.

2. Créer et activer ta branche

git switch -c ab/corriger_calcul_score

switch change la branche active et -c demande d’en créer une nouvelle. Remplace ab par tes initiales. Ta correction non commitée est conservée.

3. Relire, puis préparer le fichier

git diff -- app/src/main/java/fr/stageacademy/quiz/MainActivity.kt

Vérifie le passage de 0 à 4. Si l’affichage ouvre un lecteur, appuie sur q pour le quitter.

git add app/src/main/java/fr/stageacademy/quiz/MainActivity.kt
git diff --cached
git status

add prépare ce fichier pour le prochain commit. diff --cached montre ce qui est réellement préparé. Vérifie qu’il n’y a que la correction attendue, même si d’autres fichiers avaient déjà été préparés.

4. Enregistrer le commit

git commit -m "[QuizScore] Corrige le calcul des points par question"
git log -1 --oneline
git status

-m donne le message du commit. log -1 --oneline affiche le dernier commit sur une ligne. Le statut ne doit plus signaler de modification en attente pour ta correction.

5. Envoyer la branche sur ton fork

git push -u origin ab/corriger_calcul_score

Utilise le même nom qu’à la création de la branche. push envoie les commits ; -u relie ta branche locale à la branche distante pour les prochains échanges. Attends le message de réussite.

Git peut afficher un lien pour ouvrir une PR sur GitHub. Ce lien ne crée pas la PR à ta place. Le Git du terminal ne crée pas de PR à lui seul : la prochaine étape se fait avec l’intégration GitHub de l’IDE ou dans le navigateur.

Aide commune · Git demande mon nom et mon adresse

Git inscrit une identité d’auteur dans les commits. Avec l’encadrant, remplace les deux exemples ci-dessous par ton nom d’auteur et l’adresse choisie pour tes commits. Ton adresse GitHub privée « noreply » est disponible dans les paramètres d’adresse e-mail de ton compte. Cette identité est distincte de la connexion qui autorise le push.

git config --local user.name "TON_NOM_AUTEUR"
git config --local user.email "TON_ADRESSE_DE_COMMIT"

--local limite ces réglages à ce dépôt. Reprends ensuite l’étape du commit ; tu n’as pas besoin de recréer la branche.

Aide commune · Le push est refusé ou ne se termine pas

Lis le message avec l’encadrant : connexion GitHub, droits sur le fork ou branche distante déjà existante peuvent demander une action différente. Si Git indique que l’historique distant a avancé, examinez les changements avant de choisir comment les récupérer. Ne force pas le push et ne supprime pas ton travail pour contourner le message.

💡

Commit · étape enregistrée

Une étape de l’historique local, avec les changements sélectionnés et un message. Notre convention [FeatureName] Message aide à repérer le sujet.

💡

Préparer · stage / add

Choisir les changements qui entreront dans le prochain commit. Enregistrer le fichier dans l’éditeur ne fait pas cette sélection.

💡

Push · envoyer

Envoyer les commits d’une branche vers un dépôt distant. Cela ne les intègre pas automatiquement dans dev.

💡

Checkout / switch

Activer une branche pour travailler dessus. Le nom affiché dans l’IDE indique la branche active.

💡

Log · historique Git

Ici, la liste des commits. Cet historique Git est distinct de Logcat, qui affiche les messages de l’application en cours d’exécution.

03 / Proposer le changement

Ouvre une PR dans ton propre fork.

Les deux chemins se rejoignent ici. La destination de cet exercice est le dev de ton fork. Vérifie les noms des dépôts : un outil peut proposer par défaut le dépôt d’origine.

Depuis : TON_PSEUDO/stage_academy · ab/corriger_calcul_score

Vers : TON_PSEUDO/stage_academy · dev

Créer la PR depuis l’intégration GitHub de l’IDE
  1. Si nécessaire, connecte ton compte avec l’encadrant dans Settings → Version Control → GitHub (paramètres → gestion de versions → GitHub).
  2. Si l’action est disponible, ouvre Git → GitHub → Create Pull Request, ou la fenêtre Pull Requests et son action de création.
  3. Choisis comme dépôt de destination (base) ton fork et la branche dev. Comme source (head), choisis ton fork et ta branche de correction.
  4. Relis le diff, complète le titre et la description ci-dessous, puis clique sur Create Pull Request.

Android Studio repose sur la plateforme IntelliJ ; la présence de cette action dépend de la version et de l’intégration GitHub installée. Si elle manque ou ne permet pas de choisir ton fork comme destination, passe au navigateur. Le commit et le push restent déjà faits.

Créer la même PR sur GitHub si nécessaire
  1. Ouvre GitHub, puis ton dépôt TON_PSEUDO/stage_academy.
  2. Choisis Pull requests → New pull request, ou la bannière Compare & pull request après le push.
  3. Vérifie le dépôt de destination et la branche base: dev, puis le dépôt source et la branche compare: ab/corriger_calcul_score. Les deux dépôts doivent être ton fork ; ajuste les sélecteurs, ou utilise compare across forks si nécessaire.
  4. Relis les différences et crée la PR avec le titre et la description ci-dessous.

Un titre qui annonce le résultat

[QuizScore] Corrige le calcul des points par question

Une description courte et vérifiable

Problème : un clic sur « Click me » arrêtait l’application.
Cause : le calcul divisait 100 par zéro.
Correction : utiliser 4 questions pour cet exercice.
Vérification : après relance et clic, l’app reste ouverte
et le bouton affiche « 25 points par question ».

Décris uniquement un test que tu as réellement fait. La correction utilise encore une valeur d’exemple ; le vrai nombre de questions sera traité plus tard.

Une PR ouverte est une proposition à relire.

Vérifie qu’elle contient ta correction et laisse-la ouverte pour la relire avec l’encadrant. La création de la PR n’a pas encore fusionné la branche dans dev.

💡

PR · pull request

Une demande pour relire et intégrer les changements d’une branche dans une autre. Elle rassemble le diff, les échanges et les vérifications.

💡

Base / head / compare

Base : la branche qui recevrait les changements. Head ou compare : la branche qui les propose. Ici, les deux appartiennent à ton fork.

💡

Revue · review

Lire les changements et vérifier qu’ils répondent au problème. La description explique ce qui a changé et comment cela a été vérifié.

💡

Fusionner · merge

Intégrer les changements d’une branche dans une autre. On garde cette étape pour la revue avec l’encadrant.

04 / Ton travail est visible

Retrouve les traces de chaque étape.

À montrer à ton encadrant

Ces cases sont tes confirmations. Le guide n’exécute aucune commande, ne consulte pas ton compte et ne sauvegarde pas ta progression.

Question : mon push a réussi. Mon changement est-il déjà dans dev ?

Non. Le push a envoyé les commits sur ta branche distante. La PR propose leur intégration ; la fusion, après revue, est une autre action.

Avant les exercices de code : retrouver la version acceptée.

Fais relire la PR avec l’encadrant. Si la correction est acceptée, fusionnez-la dans le dev de ton fork, puis actualisez ce dev dans ton clone. Depuis un état Git sans modification en attente, le terminal permet de faire :

git switch dev
git pull --ff-only

pull récupère ici la mise à jour distante ; --ff-only demande une avancée directe de la branche. Si Git refuse, lis le message avec l’encadrant sans forcer. Vérifie que le bouton affiche toujours « 25 points par question ». La prochaine branche doit partir de cette version corrigée. Si la revue n’est pas terminée, garde ton travail et reprends ce point avec l’encadrant avant de changer de base.

Enregistrer → tester → commit → push → PR : tu sais maintenant expliquer le rôle de chaque étape depuis ton IDE.

Une donnée qui survit aux objets

Créer et retrouver ton profil.

Ajoute un nom de joueur, valide sa photo et retrouve le profil après relancement. Relie la vue, le presenter et le stockage avec des responsabilités explicites.

Prérequis : Profil et la capture temporaire fonctionnent dans ton clone. La réalisation est accompagnée par l’encadrant et l’agent ; le guide n’enregistre rien à ta place.

01 / Faire durer le résultat

Créer un profil, fermer l’app et le retrouver.

Profil permet déjà de prendre une photo temporaire. Ajoutons maintenant un nom de joueur et un bouton « Enregistrer le profil ». Le résultat attendu est simple : après une sauvegarde réussie et un nouveau lancement, le nom et la photo enregistrés sont retrouvés.

  • Le nom est obligatoire et ne peut pas être composé seulement d’espaces.
  • La photo est facultative : un profil sans photo utilise un visuel par défaut.
  • Modifier le formulaire prépare un brouillon ; cela ne remplace pas immédiatement le profil enregistré.
  • Une nouvelle photo devient celle du profil seulement après « Enregistrer ».

Le refus de caméra ne bloque ni le profil sans photo ni le quiz. Nous conservons un seul profil local, sans compte, mot de passe, serveur ou synchronisation entre appareils.

La réussite doit être observable après relancement.

Le nom qui reste affiché quand on change d’onglet ne suffit pas à prouver la sauvegarde. L’app doit pouvoir relire les données après la fin de son processus.

DataStore conserve ici de petites données sous forme de clés et de valeurs. On y enregistre le nom du joueur et une référence au fichier photo, pas la photo complète. Ses lectures et écritures utilisent les coroutines ; ses données peuvent aussi être lues par un Flow.

Le fichier validé doit quitter le cache pour un emplacement comme filesDir/profile_photos/. Ce stockage privé ne nécessite pas de permission générale de stockage. Il survit au relancement, mais l’effacement des données ou la désinstallation peut le supprimer : ce n’est pas une sauvegarde extérieure à l’app.

Les pages officielles sur DataStore et les fichiers privés expliquent ces emplacements.

03 / Garder les responsabilités lisibles

Le modèle décrit ; le stockage conserve ; la vue présente.

Le modèle est hors du package de vue, comme Question. Les noms du code restent en anglais :

package fr.stageacademy.quiz

data class PlayerProfile(
    val displayName: String,
    val photoFileName: String?,
)

displayName signifie « nom affiché ». photoFileName est le nom du fichier validé dans le dossier privé du profil ; null signifie qu’aucune photo n’est associée.

On distingue aussi l’accès au stockage du rôle du presenter. Voici un exemple de contrat pour cet accès, à adapter dans l’intégration :

package fr.stageacademy.quiz

interface ProfileStorage {
    suspend fun load(): PlayerProfile?

    suspend fun save(
        displayName: String,
        pendingPhotoPath: String?,
    ): PlayerProfile
}

load relit le profil, ou retourne null s’il n’existe pas. save retourne la version réellement enregistrée après réussite. Dans cet exercice, un chemin candidat nul conserve la photo enregistrée si elle existe ; pour un nouveau profil, il permet de rester sans photo. Supprimer volontairement une photo n’est pas une fonction ajoutée ici.

  • ProfileView présente les champs, l’attente, les erreurs et la confirmation.
  • ProfilePresenter vérifie le nom, coordonne le brouillon et demande la sauvegarde.
  • ProfileStorage et son implémentation relisent et écrivent les petites données ainsi que le fichier validé.
  • MainActivity crée et transmet les objets nécessaires, comme dans les étapes précédentes.

Les fichiers d’écran restent dans profile_view. Le modèle et le stockage peuvent rester à la racine du package pour cette petite app : le suffixe _view sert aux groupes MVP, pas à tous les fichiers.

Faut-il un graph, une factory ou un framework ?

Pas pour cette étape. Fais créer et passer explicitement le stockage au presenter. Avec l’encadrant, vérifie qu’il n’y a qu’une instance DataStore active pour le même fichier dans le processus, et qu’elle n’est pas recréée à chaque affichage.

Ces extraits décrivent le modèle et un contrat. Ils ne fournissent pas seuls l’implémentation DataStore ou le formulaire complet. L’agent adaptera le presenter et son contrat existants sans effacer le travail caméra.

04 / Valider une modification

Le succès arrive après les écritures, pas avant.

  1. Le joueur prépare son brouillon.

    Il saisit un nom et peut prendre une nouvelle photo. Le profil enregistré précédent reste intact.

  2. Le presenter vérifie le nom.

    Les espaces autour sont retirés ; un nom vide produit une explication, pas une sauvegarde.

  3. La vue montre l’attente.

    Le bouton évite plusieurs sauvegardes en même temps. Le texte saisi est conservé si un problème survient.

  4. Le stockage prépare une nouvelle photo si nécessaire.

    La candidate est copiée dans un nouveau fichier privé persistant, sans écraser l’ancienne image.

  5. Les données du profil sont enregistrées.

    Le nom et la référence de la photo sont mis à jour ensemble dans DataStore. Après succès, le résultat est relu dans l’état affiché et la vue confirme l’enregistrement.

  6. Les anciens fichiers devenus inutiles sont nettoyés.

    L’ancienne photo n’est supprimée qu’après la réussite de la nouvelle sauvegarde. Les fichiers ne doivent pas s’accumuler à chaque essai.

Si la copie ou l’écriture échoue, l’app ne doit pas annoncer « Enregistré » et doit conserver le profil précédent. Le brouillon reste disponible pour corriger ou réessayer.

DataStore protège-t-il aussi automatiquement le fichier photo ?

Non. La mise à jour des valeurs DataStore et la copie d’un fichier image sont deux opérations distinctes. L’ordre de préparation, de validation et de nettoyage doit éviter une référence vers une nouvelle photo qui n’a pas été créée. Une interruption peut laisser un fichier non référencé à nettoyer ; elle ne doit pas faire détruire l’ancien profil avant validation.

Un bouton « Annuler les modifications » revient au profil enregistré et abandonne la candidate. Il ne supprime pas la photo validée. Une capture interrompue ou échouée ne remplace pas non plus celle-ci.

💡

Validation

Le contrôle qui permet de décider si les données répondent aux règles, ici un nom utilisable.

💡

Confirmation

Un message fondé sur la réussite de l’opération, pas seulement sur le clic.

💡

Erreur d’écriture

Un échec pendant l’enregistrement, par exemple un fichier impossible à créer. Le formulaire doit permettre de comprendre et de réessayer.

05 / Repartir des données enregistrées

Chargement et édition sont deux moments différents.

Au démarrage ou à la première ouverture du profil, l’app relit les données enregistrées. La vue distingue « Chargement », l’absence de profil, un profil trouvé et une erreur de lecture.

Une fois le chargement terminé, le nom et la photo alimentent l’affichage. Quand le joueur commence à modifier le formulaire, ne relance pas une lecture qui écraserait sa saisie à chaque recomposition ou changement d’onglet.

Après une sauvegarde réussie, le résultat retourné devient la nouvelle référence du formulaire. Les simples propriétés du presenter ne mettent pas Compose à jour toutes seules : garde des liens explicites entre résultat reçu et état affiché.

Pourquoi une photo peut-elle manquer alors que le nom est retrouvé ?

Les métadonnées et le fichier sont distincts. Si le fichier n’est plus lisible, l’app garde le nom, montre un visuel de remplacement et permet de reprendre une photo. Elle ne doit pas planter ni promettre une image retrouvée.

Que devient la permission caméra pour relire la photo enregistrée ?

La photo appartient maintenant aux fichiers privés de l’app. La relire ne demande pas de réactiver la caméra. L’accord caméra est vérifié seulement lorsque le joueur souhaite en prendre une nouvelle.

Une lecture absente et une erreur ne sont pas la même situation. En cas d’erreur, montre une explication et une action de réessai plutôt que d’écraser silencieusement le profil comme s’il n’avait jamais existé.

Chargement · loading

La période pendant laquelle l’application attend le résultat d’une lecture.

💡

État de référence

La version enregistrée à partir de laquelle on prépare un nouveau brouillon ou annule les modifications.

07 / La preuve vient du relancement

Prévois ce qui doit rester et ce qui peut disparaître.

  1. Sur une installation de travail sans profil, vérifie l’état initial. Essaie d’enregistrer un nom vide ou fait d’espaces : aucune création ne doit être confirmée.
  2. Enregistre un nom sans photo, puis arrête et relance l’app avec l’encadrant : retrouve le nom et le visuel par défaut.
  3. Prends une photo et change le nom, puis annule. Le profil précédent doit rester la référence.
  4. Prépare à nouveau un nom et une photo, puis enregistre. Attends la confirmation avant de quitter.
  5. Avec l’encadrant, arrête réellement le processus, par exemple par « Forcer l’arrêt » dans les paramètres de l’app, puis relance-la. Ne désinstalle pas et n’efface pas les données pour ce contrôle. Retrouve le nom et la photo.
  6. Sur une installation de test, vide seulement le cache depuis les paramètres si cette action est disponible. Au relancement, le profil validé doit rester lisible : sa photo n’est plus dans ce cache.
  7. Renomme le joueur sans reprendre de photo. Après sauvegarde et relancement, le nouveau nom et la même photo doivent être retrouvés.
  8. Demande à l’encadrant de vérifier un cas d’image manquante ou d’écriture échouée dans un environnement de test. Si le cas n’est pas reproduit, indique-le comme non vérifié ; n’affirme pas qu’il est couvert par un simple succès.
  9. Vérifie enfin le quiz, son score et son recommencement. Sauvegarder un profil ne sauvegarde pas automatiquement la partie.
Mes repères

Notes et confirmations personnelles sans envoi ni sauvegarde. Le guide ne crée aucun profil, ne lit pas ton stockage et ne vérifie pas ton appareil. Copie tes notes avant de fermer la page.

Après validation avec l’encadrant, conserve le travail dans Git et complète ton bilan : explique ce qui était en mémoire, ce qui a été écrit et ce que tu as réellement retrouvé au lancement.

Une information peut arriver plus tard

Attendre sans bloquer l’écran.

Comparer une réponse est rapide. Lire un fichier ou attendre une donnée peut prendre plus longtemps. Comment garder l’application utilisable et afficher la valeur quand elle arrive ?

Nous découvrons synchrone, asynchrone, coroutine et Flow avec une source fictive de meilleur score. La démo ne lit aucun stockage et ne modifie pas les points du quiz.

01 / Quand récupère-t-on le résultat ?

Synchrone et asynchrone.

Un appel synchrone réalise son travail avant de rendre la main. Notre comparaison de deux textes est un bon exemple : le résultat est disponible quand l’appel revient.

Un travail asynchrone peut se terminer plus tard, pendant que le programme continue à traiter d’autres actions. Il faut prévoir comment recevoir son résultat.

Sur Android, le thread principal prend notamment en charge l’interface. Si on le bloque longtemps avec un travail lent, l’écran répond mal. Rendre un travail asynchrone ne le rend pas forcément plus rapide : cela permet surtout d’organiser l’attente et les autres actions.

Ces idées ne sont pas propres à Kotlin. Les mots et les outils changent selon les langages, mais le besoin reste le même.

💡

Synchrone · synchronous

L’appel finit son travail avant de rendre la main à son appelant.

💡

Asynchrone · asynchronous

Le résultat peut arriver plus tard ; son traitement est organisé sans imposer de bloquer l’appelant pendant toute l’attente.

💡

Thread · fil d’exécution

Une ressource sur laquelle du code s’exécute. Le thread principal de l’app doit rester disponible pour l’interface.

02 / Une tâche qui peut attendre

Coroutine et mot-clé suspend.

Une coroutine permet d’organiser une tâche qui peut suspendre son exécution puis reprendre. Pendant une suspension adaptée, elle ne bloque pas le thread juste pour attendre.

Voici une fonction de lecture fictive, pour comprendre un résultat unique :

private suspend fun readDemoBestScore(): Int {
    delay(1500)
    return 2
}

suspend permet à cette fonction d’utiliser des opérations suspendables. delay(1500) attend environ 1,5 seconde sans bloquer le thread, puis la fonction renvoie 2. C’est un délai volontaire pour l’exercice, pas une vraie lecture de fichier.

Le travail reste écrit dans l’ordre : attendre, puis renvoyer. Suspend ne signifie ni « lancer tout seul » ni « exécuter forcément sur un autre thread ». Cette fonction doit être appelée depuis une coroutine ou une autre fonction suspendable.

Une opération qui bloque réellement un thread ne devient pas non bloquante en ajoutant suspend. Dans une vraie lecture, on choisira les outils adaptés au travail ; les détails des threads et des dispatchers ne sont pas nécessaires à cet exercice.

Faut-il utiliser Thread.sleep pour simuler l’attente ?

Non dans cette démo d’interface. Thread.sleep bloque le thread sur lequel il est exécuté. Nous utilisons delay dans une coroutine pour observer une attente qui laisse l’interface disponible.

💡

Coroutine

Une tâche dont l’exécution peut être suspendue puis reprise. Elle a un contexte et une durée de vie, pas une existence indépendante de l’application.

💡

suspend

Le mot-clé d’une fonction qui peut participer à ce mécanisme. L’appel peut finir tout de suite ou suspendre selon le travail réellement fait.

💡

delay · délai

Une attente suspendable fournie par la bibliothèque de coroutines. Ici, 1500 représente des millisecondes.

03 / Recevoir des valeurs au fil du temps

Un résultat unique ou un Flow ?

Une lecture suspendable peut fournir une valeur à son retour. Un Flow<Int> permet de recevoir des entiers au fil du temps. Un flux peut n’émettre aucune valeur, en émettre une ou plusieurs, puis se terminer.

Voici la source utilisée dans notre démo :

private fun observeDemoBestScore(): Flow<Int> {
    return flow {
        delay(1500)
        emit(2)
        delay(1500)
        emit(4)
    }
}

flow { … } décrit comment produire les valeurs. emit(2) transmet 2 ; plus tard, emit(4) transmet 4. Ce Flow précis commence son travail lorsqu’on le collecte. Une nouvelle collecte recommence ce petit scénario.

Pour recevoir chaque valeur, on utilise collect :

observeDemoBestScore().collect { bestScore: Int ->
    bestScoreLabel = "Meilleur score démo : $bestScore"
}

Le bloc reçoit chaque entier dans bestScore et met à jour le texte. Il ne parcourt pas une liste déjà complète : les valeurs peuvent arriver plus tard. Dans notre exemple, la collecte se termine après la deuxième émission.

Flow transporte des valeurs ; il ne les sauvegarde pas.

DataStore peut fournir un Flow de données lues sur disque. Notre source ci-dessus contient seulement deux nombres écrits dans le code : aucun meilleur score réel n’est calculé, enregistré ou restauré.

💡

Flow · flux

Une source de valeurs que l’on peut collecter. Ici, elle fournit des Int à deux moments différents.

💡

emit / collect

Emit produit une valeur ; collect reçoit les valeurs et exécute le bloc prévu pour chacune.

💡

bestScore / bestScoreLabel

« Meilleur score » / « texte du meilleur score ». Dans cette page, ces valeurs appartiennent à une démonstration fictive.

04 / Qui démarre et qui arrête ?

Une tâche doit avoir un propriétaire.

Pour cette observation liée à l’interface, nous utilisons un cadre Compose fourni :

LaunchedEffect(Unit) {
    observeDemoBestScore().collect { bestScore: Int ->
        bestScoreLabel = "Meilleur score démo : $bestScore"
    }
}

LaunchedEffect démarre une coroutine quand cette partie entre dans la composition. Quand cette partie en sort, sa coroutine est annulée. Une clé qui change provoquerait aussi un redémarrage ; Unit reste constant dans notre démo pour ne pas relancer la collecte à chaque recomposition.

Nous allons retirer la partie observatrice avec un if. Cela permet de voir une annulation pendant delay. Réafficher cette partie crée une nouvelle observation qui repart du début.

Annulé signifie-t-il que tous les travaux s’arrêtent instantanément ?

L’annulation demande à la tâche de s’arrêter. Elle est coopérative : des opérations adaptées comme delay y réagissent. Un calcul qui tourne sans coopérer ou un appel bloquant ne devient pas interrompable par magie.

Masquer la démo et mettre l’app en arrière-plan sont-ils identiques ?

Non. LaunchedEffect suit ici la composition. Passer l’app à l’arrière-plan ne retire pas forcément ce bloc. Pour une vraie observation de données d’écran, on choisit aussi un outil adapté à la visibilité et au cycle de vie Android, par exemple une collecte sensible au cycle de vie. L’exercice observe la disparition réelle du bloc avec notre bouton.

On ne lance pas une tâche sans propriétaire pour qu’elle continue « au cas où ». Une sauvegarde durable n’est pas non plus garantie simplement parce qu’une coroutine a été lancée.

💡

Scope de coroutine

Le cadre qui rattache une tâche à un propriétaire et organise sa durée de vie. Le cadre est fourni par LaunchedEffect dans notre exemple.

💡

Annulation · cancellation

Une demande d’arrêt d’une tâche devenue inutile. Ce n’est pas la même chose qu’un échec de lecture.

💡

LaunchedEffect

Un outil Compose pour lancer ici une tâche liée à la présence du bloc dans la composition. Nous n’avons pas besoin d’en détailler toutes les possibilités.

05 / Une petite expérience dans le quiz

Afficher, attendre, masquer.

Avec l’encadrant, prépare une branche depuis ton quiz fonctionnel, par exemple ab/observer_flux_demo. La démonstration reste séparée des règles du presenter et du score de la partie.

  1. Dans MainActivity.kt, ajoute les imports ci-dessous s’ils manquent.
  2. Ajoute observeDemoBestScore et AsyncBestScoreDemo au niveau du fichier, après les fonctions existantes. Ce sont deux ajouts, pas des remplacements de QuizPresenter ou de QuestionView.
  3. Dans le Column principal de WelcomeScreen, après le Text du titre et avant le if qui choisit la question ou la fin, ajoute l’appel AsyncBestScoreDemo(). Le défilement existant garde tous les éléments accessibles.

import kotlinx.coroutines.delay

Les outils d’état, Button, Text, Column, Arrangement et dp sont déjà utilisés dans ce projet. Les imports kotlinx.coroutines utilisent la bibliothèque de coroutines apportée par les dépendances Compose de notre base. Si l’IDE ne les résout pas, vérifie la synchronisation et les dépendances avec l’encadrant ; ne change pas une version au hasard.

Vue de démonstration complète à ajouter
@Composable
private fun AsyncBestScoreDemo() {
    var isDemoVisible: Boolean by remember { mutableStateOf(true) }

    Column(verticalArrangement = Arrangement.spacedBy(8.dp)) {
        Text(text = "Meilleur score : démonstration sans sauvegarde")
        Button(onClick = { isDemoVisible = !isDemoVisible }) {
            Text(text = "Afficher / masquer la démo")
        }
        if (isDemoVisible) {
            var bestScoreLabel: String by remember {
                mutableStateOf("Chargement de la démo…")
            }
            LaunchedEffect(Unit) {
                observeDemoBestScore().collect { bestScore: Int ->
                    bestScoreLabel = "Meilleur score démo : $bestScore"
                }
                bestScoreLabel = "$bestScoreLabel — source terminée"
            }
            Text(text = bestScoreLabel)
        }
    }
}

Le bouton reste visible en dehors du if. Il peut donc retirer puis réafficher la zone qui contient le texte et LaunchedEffect. Les deux valeurs d’affichage sont locales à cette démonstration.

La mention « source terminée » apparaît quand collect a reçu les deux valeurs et s’est terminé normalement. Masquer le bloc pendant l’attente annule la collecte : ce n’est pas une troisième valeur.

Pourquoi ne pas mettre collect directement dans le corps de WelcomeScreen ?

Collect est une opération suspendable, et une fonction Compose peut être réexécutée pour décrire l’interface. LaunchedEffect fournit le cadre de lancement et d’arrêt, au lieu de démarrer un nouveau travail à chaque description.

💡

Démonstration · demo

Un exemple contrôlé pour comprendre le mécanisme. Son résultat ne prouve pas qu’un fichier a été lu ou qu’un vrai meilleur score a été sauvegardé.

06 / Prévoir, observer, expliquer

Qu’arrive-t-il à la tâche et à l’écran ?

  1. Lance l’app : la zone de démo indique le chargement. Après environ 1,5 seconde, elle affiche 2 ; environ 1,5 seconde plus tard, 4 et « source terminée ».
  2. Pendant l’attente, essaie un bouton du quiz. L’interface doit rester utilisable ; le vrai score suit ses règles habituelles et n’est pas remplacé par 2 ou 4.
  3. Masque puis réaffiche la démo. Elle revient au chargement : c’est une nouvelle collecte de notre source.
  4. Réaffiche puis masque rapidement, avant la première valeur. L’observation est annulée et le texte n’est plus dans l’interface.
  5. Réaffiche encore : le scénario commence de nouveau au début. Décris le lien entre entrée du bloc, attente, émission, collecte et sortie.
Le score de la démo change, mais pas celui de la partie : est-ce normal ?

Oui. La démo écrit dans bestScoreLabel. Les points de la partie sont conservés dans le presenter puis relus dans displayedScore. Ce sont des informations différentes.

Dans un vrai stockage, que faudrait-il prévoir en plus ?

La lecture et l’écriture réelles, leurs erreurs possibles, la valeur initiale et la bonne durée de vie de l’observation. Il faudrait aussi décider qui possède le stockage et comment les valeurs lues deviennent de l’état affiché. Le délai fictif de cette page ne réalise pas ces opérations.
